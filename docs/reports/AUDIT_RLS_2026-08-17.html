Why this class was invisible

The app connects as govtech_app, a NOBYPASSRLS role. The sandbox connected as govtech — a superuser, which bypasses every row-level security policy unconditionally, including FORCE.

So a route that forgot to establish its tenant context worked perfectly in the sandbox, passed tsc, passed vitest, passed a live browser drive — and then returned zero rows in production. Not an error. Just nothing: an empty list, a 404, a silently-skipped write.

Connecting as the real role makes the whole class immediate and obvious:

$ psql -U govtech_app # the role production actually uses TABLE NO CONTEXT WITH CONTEXT ────────────────────────────────────────────────────────── proposal_portals 0 4 proposals 0 5 proposal_sections 0 65 library_atoms 0 33 atom_tags 0 134 agent_task_queue 0 2 Every RLS-gated table returns nothing without SET app.tenant_id.

The sandbox has been switched to serve as govtech_app with DATABASE_URL_OWNER for sqlBypass — which is what CLAUDE.md already said it should do. A route that forgets its context now fails here, which is the entire point.

The mechanic that caused most of them

enterTenant uses AsyncLocalStorage.enterWith(). Called inside an awaited helper, it is discarded the moment control returns to the handler — Next.js wraps each request in its own .run(), so the handler's post-await continuation never sees it. The gate looked present in the code and was gone at runtime.

Fix: enterTenant belongs in each handler's own frame. Shared library functions instead use runInTenant, which opens its own scope and is correct regardless of caller.

Two things that looked like bugs and were not

Open — your call

1 · Where platform curation memory lives — RESOLVED (migration 186)

I first filed it under the house rfp-pipeline tenant, because the column was NOT NULL REFERENCES tenants(id) and mig 152 files the system_starter library that way. Eric's counter settled it: the role has to descend into tenant space to curate a tenant proposal, so why would memory not be enforced the same way?

That is the right rule. Curation is platform work by construction — all four writers are tenantScoped: false and act on the MASTER curated_solicitations before any tenant mirror exists. Filing it under a tenant conflates platform knowledge with that one tenant's own memory, and hands the whole curation history to anyone holding its context. My mig-152 precedent was also weaker than I presented: the starter library is a source shelf tenants copy forward from, which curation memory never is.

Migration 186 drops the NOT NULL so platform scope is tenant_id = NULL — the same marker tasks and process_instances already use. The policy is deliberately left as tenant-equality (no OR tenant_id IS NULL read branch), which is stricter than the tasks precedent: platform memory is reachable only through an explicit bypass, and never from tenant space. Proven live as govtech_app:

1. platform write via sqlBypass INSERT 0 1 2. visible to a TENANT context? 0 ← descent enforced 3. memory.search filter (tenant_id = $tenant) 0 ← excluded everywhere 4. compliance-suggest (bypass, namespace-scoped) 15 ← pre-fill still works

2 · A failed action step re-runs on HITL resume

Recovery skips only steps marked completed, so a failed action ahead of an independent human gate would re-execute its side effects on resume. No current template has that shape, so I left it — it is a real trap for the next template that does.

3 · I cannot certify zero bugs

What I can say precisely: the RLS-context class is now swept and, more importantly, the sandbox can no longer hide it. The agent archetypes and workflow templates were read end to end. Everything claimed above was verified by moving real data and watching the result — not by reading code and concluding.
