The defect that mattered most

Found by reading what the draft said, not whether the workflow succeeded

A technical section for topic OSW26BZ04-DP013 opened by citing a different agency's solicitation from two years earlier. Not a formatting nit — a reviewer reading that is reading a proposal that appears to be for another program. It had four independent causes, and each had to be fixed separately.

Cause 1 · retrieval

The drafter quoted the wrong 2,000 characters

Results came back as content[:2000] — the opening of whatever matched. On a 13,000-word past proposal that is its cover sheet: title block, agency, proposal number. The search also matched on substring anywhere in a document, ranked by updated_at rather than relevance, and carried none of the canonical selector's scope rules.

Results now quote the window that actually matched, discounted for table-of-contents shape — a contents list names every section verbatim, so it out-scores the section's own prose on any title query while containing none of it.

Cause 2 · ingest

Every atom carried the source document's running header

Page-grain atomization kept whatever the word processor repeats on every page. On a DSIP submission that is the solicitation's own identifiers, welded into every atom:

Topic: X23.5_CSO Proposal Number: FX235-CSO1-0859

Detection is structural — a line repeating across a run of pages — so it holds for footers we have never seen. Three refinements came out of running it against the four filed Immobileyes proposals rather than fixtures: a run is measured against its own span, because a merged package is several documents each with its own header; a run must reach eight pages, because density alone cannot tell a header from a cost table that spans four; and page-number collapsing applies only to lines that are page numbering. That last one was live and destructive — any sentence citing a page was collapsible, and variant expansion then deleted real prose from every page.

Cause 3 · provisioning

A mold displaced the computed cost workbook

The mold builder stamped a skeleton onto the cost volume's spreadsheet item. That mold is cost_volume-typed, and provisioning treats a cost-typed mold there as a deliberate admin override — so it never computed the workbook. The cost section arrived as a bare heading, the drafter filled it from the library, and the "cost volume" became prose lifted from a past proposal. It priced nothing.

Two features each correct alone, wrong together — the same shape as the mold-seeding / anti-clobber pair fixed earlier in the night. The rule for which item receives the workbook now lives in one place that both sides read.

Cause 4 · the part the library cannot fix

A cover sheet legitimately carries its own solicitation's numbers

That is the content of those pages — it cannot be stripped at ingest without deleting real data. So the control moved to the compliance floor: each artifact now carries its own topic and solicitation number, and any labelled identifier that is not one of them is reported as foreign_solicitation at section save and at the export gate.

It fired on exactly two volumes. One was real. The other — a genuine prior Air Force contract in the past-performance narrative — was a false positive, so contract and award came out of the label set. A contract number is a record of work performed, not a claim about which solicitation this is.

Everything else that was broken

Each looked like success until something read the output

Workflow

The full-draft workflows could not draft

draft_sections was a single agent call passing only a proposal id to an archetype built to draft one section from its title, budget and ranked atoms. It defaulted the title to "Untitled Section" and made one contextless call for the whole proposal. Twenty sections in, one blob out, workflow reports success.

Review

The color team's findings were thrown away at the last step

Reviews ran, comments appeared on every section, and what a builder read was "Review: Acceptable — meets minimum requirements." That is the one-line label written for episodic memory; it was being preferred over the review itself. The disqualifier audit, the weaknesses, the risks and the recommendations were all computed and discarded.

The verdict was not the review's own either — the score was found by scanning the whole document for the first ladder word, best-first. A Marginal review whose weaknesses said "no good evidence of a transition path" was recorded as Good.

Submission

A finished build was unsubmittable for a document that does not exist

Five hard blockers, one of them "CMMC Reps & Certs" — a requirement from a program skeleton's hard-coded default list, not from this BAA. CMMC is a representation made inside DSIP; there is no file to upload. The only escape was an admin waiving a requirement nobody could verify.

The provenance was already recorded and the column to carry it already existed; they were not connected. A defaulted requirement is now a warning that says where it came from; one read from the solicitation still blocks. Both stay on the checklist.

Data loss

The save route accepted anything shaped like an object

A drive script sent the canvas rules object back as a document and replaced 20 drafted sections with an empty shell — 4,000 characters each down to a 277-byte husk, no error, HTTP 200. Nothing was lost: version history had archived every draft and all 20 came back through the product's own restore route. The trust hub did exactly what it exists for. The route now requires a document.

Fixture

Three "fresh provision" runs were the same stale build

The reset script hit a foreign-key violation, aborted its transaction, skipped every later statement — and still exited 0 and printed success. The drive then took its already-purchased branch and quietly reused the old proposal, so the cost-workbook fix looked like it had not worked. Worth stating plainly: a lying fixture invalidates everything downstream of it.

What I did not finish, and what is not what it looks like

Sandbox limit

The prose is stitched, not written

There is no live model key here, so the committed emulator stands in for Claude — by design, on the identical wiring prod uses. It composes each section from the customer's own library atoms and nothing else, which keeps the harness honest about retrieval: a thin library yields a thin draft. But it is sentence-stitching, not writing. The Technical Volume carries 19,298 characters of on-topic, correctly-sourced content that reads choppily. The pipeline is proven; the prose quality is not. That needs one run with a real key.

Known gap

A letter-spaced identifier slips the check

Some DSIP cover sheets render the number as F 2 - 1 7 5 2 8. The detector reads a contiguous token and misses that form. There is a test that asserts the miss, so it stays visible rather than being mistaken for coverage.

Known gap

The atomizer names atoms after page headers

Library atoms arrive titled p11 · 2.1.1 Identification and Significance… — page-derived, with numbering baked in. Retrieval works despite it, but those titles surface in the workspace and occasionally bleed into drafted text. Not fixed tonight.

Judgement call

The character cap is 3,000, not 3,500

Your note said 3,500. The BAA states 3,000, the DSIP form you screenshotted shows 0 / 3000 characters on both fields, and the filed Technical Abstract measures 3,002 characters with whitespace collapsed — written right up to the cap. I built to 3,000, read from source and cited. Flagging it because I went against what you wrote.
