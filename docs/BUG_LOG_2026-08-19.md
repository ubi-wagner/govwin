## B1 — The heartbeat did not supervise the pipeline worker · FIXED
**Where** `frontend/scripts/sandbox-heartbeat.sh`

## B2 — "Never double-starts" guard depended on a binary that is not installed · FIXED
**Where** `frontend/scripts/sandbox-heartbeat.sh`
**Proven** `command -v ss` → missing in this container. The guard was
`ss -ltn | grep -q ':3000'`, so it ALWAYS evaluated false; on any cycle where `/login` was not yet
200 the script fell through to `start_server`. A Next standalone boot takes several seconds, so a
restart reliably spawned a second server, which then fought for :3000.
**Why it matters** The file header states "never double-starts if something already owns :3000".
The code promised something it could not do, and the failure mode was silent contention rather
than an error.
**Fix** `port_busy()` — `fuser` (present) first, `ss` retained as a fallback for hosts that have it.
**Class → sweep for** *unavailable-dependency guards*: any shell/tooling path that branches on a
command's success where the command may be absent. `command -v` before use, or pick a probe that
is guaranteed present. Also the general shape: **a comment asserting a guarantee the code does not
implement.**

# Quality bar — measured from the hand-built reference

`MIRAGE_OSW26BZ04_DP013_Patent_Holiday_Technical_Volume.pdf` is the standard the generated volumes
are judged against. Measured, not estimated:

| Property | Reference | My last run | Gap |
|---|---|---|---|
| Pages | **10 of 10** (envelope filled) | ~7 | under-filled |
| Text characters | **36,701** | 19,298 | ~half density |
| Images | **44** across 5 pages (4·11·12·3·14) | **0** | absent entirely |
| Font faces | **9** — Times NR reg/bold/italic/bold-italic · Arial reg/bold/italic · Symbol · Wingdings | 1 | no inline variation |
| Page size | Letter 612×792 pt | same | ✓ |

**The rule this sets:** fill the envelope deliberately. A 10-page cap means ~9.9 pages; a
3,500-character cap means just under 3,500. Under-filling is a failure mode, not a safe default —
an evaluator reads a half-empty volume as a half-made proposal.

**Surface that must be exercised** (Word · PPT · XLS): images, captions, inline bold/italic runs,
section headings, page headers/footers, tables, charts, bullet glyphs.

## B6 — Six RLS tables seq-scan on the exact column their policy filters · FIXED (mig 194)
**Proven**
```sql
-- RLS-enabled + has tenant_id + no index whose leading column is tenant_id
purchases · agent_task_queue · notification_read_state ·
proposal_amendment_flags · shadow_admin_grants · vault_members

```
Each carries a `tenant_isolation` policy reading

tables are still small.
**Fix** mig 194 — the six policy-column indexes, purchases' other two FKs, and five
cascade/join-relevant FKs (`tenant_bucket_scores.bucket_id` is ON DELETE CASCADE and was scanning
the whole scores table per bucket delete). All `IF NOT EXISTS`. Gap query re-run after apply:
empty.
**Class → sweep for** *the index that should follow a policy*: whenever a table gains RLS on a
column, that column needs an index. Add it in the same migration that adds the policy.

## B17 — Two "reviewed" verdicts asserted without evidence the reviewer ran · FIXED (2026-08-19)
**Where** `pipeline/src/workflows/actions/ingest_actions.py:136-148` ·
`portal_stage_actions.py:71-88` → `frontend/lib/portal-workflow.ts:511-533`
**Proven** `record_ingest_review` writes
`status='reviewed'`, `review={"resolution": …, "recorded_by": "advisory_manager"}` where
`recorded_by` is a **hardcoded string literal** and `resolution` comes from `payload.resolution`,
never from an agent result. The step is `ACTION` with `depends_on=None` — correct per the
hard-step-behind-AI invariant — so when the AI steps safe-skip (no key, rate-limited, fabric

**Class → sweep for** *provenance asserted by literal*: any `recorded_by` / `reviewed_by` /

## B30 — The engine records a safe-skipped step as "completed" · LOGGED (deliberately not fixed)
**Where** `pipeline/src/workflows/manager.py` (the `if step_result is not None:` branch) ·
every safe-skip return in `pipeline/src/workflows/processor.py`
**Proven** Live, through the real engine (`scripts/drive_b17_evidence.py`, RUN 1). With no fabric
the log says `AI_INVOKE action 'tool.advisory.reconcile' skipped (fabric=False, mapped=True)` and
the persisted record says:
```json
{"record": "completed", "review_manager": "completed"}
```
Every safe-skip returns `{"result": None, "skipped": True, "reason": …}` — a truthy dict — and the
manager writes "completed" for any step whose executor returned anything at all.
**Why it matters** Two live consequences. (1) It is what nearly defeated the B17 fix: any check
reading `step_status` cannot tell a step that worked from one that declined to. (2) The
`/admin/workflows` instance overlay reads the same map, so an operator watching a run sees a green
"completed" AI step that never called an agent — the monitor showing a healthy cohort in a
deployment with no API key.
**Why not fixed here** `depends_on` treats `'skipped'` as a reason to skip dependents. Writing the
honest status into `step_status` would cascade: `reconcile` (depends_on `refute_0`) would start
skipping whenever the refuters safe-skip, and the same shape repeats across the full-draft and
Studio workflows. That may well be the RIGHT behaviour — reconciling nothing is pointless — but it
is a semantics change to the engine with real blast radius, and it belongs in its own change with
its own drive, not inside a bug fix that had to ship correct today. B17 is closed without it:

## B24 — Retrieval never read the section's own words · FIXED

**Where** `frontend/lib/atoms.ts::selectForSection`, and the pipeline's mirror in

## B37 — The standalone server cannot be found by name, so every "restart" was a no-op · FIXED (tooling)
**Where** `scripts/sandbox-up.sh` (and every ad-hoc restart line in this session).
**Proven** `pkill -f "standalone/server.js"` exits 0 having matched nothing; `pkill -f next-server`

"restarts" reported success while the original process kept serving. The cause: Node rewrites its


**Class → sweep for** *identifying a process by a string it controls*: a title, a name, an argv.

# 2026-08-22 — the storage/provenance pass (B42–B45)

Four bugs, one shape. Every one of them sat behind a handler that caught its own failure and
carried on: a `try/except` that logged a warning, or a route that returned `201` with the error
folded into a field nobody reads. Each produced a run that **reported success having done less than
it claimed** — the state a test suite structurally cannot see, because there is nothing to fail.

The fix in each case is two-part: correct the behaviour, **and** make the failure legible in the
record it writes. Where only the first half is done, the next regression is silent again.

## B42 — The section-slug rule rejected half the shredder's own canonical vocabulary · FIXED
**Where** `pipeline/src/storage/paths.py` `_SECTION_SLUG_RE`, mirrored in
`frontend/lib/storage/paths.ts`
**Proven** The shredder's own prompt (`shredder/prompts/v1/section_extraction.txt`) enumerates ten
canonical section keys and instructs Claude to use EXACTLY those strings. The validator allowed
`[a-z0-9-]` only:
```
accepted  5/10   cover · commercialization · team · eligibility · appendix
REJECTED  5/10   technical_approach · cost_volume · evaluation_criteria
                 submission_format · compliance_requirements
```
So `rfp_pipeline_path(kind="shredded")` raised `StoragePathError` on half of every real
solicitation. `runner.py`'s per-section guard caught it, logged
`shredder: section %s S3 write failed`, and continued.
**Why it matters** These are the artifacts the comment in `runner.py` calls "what customer agents
will read from their isolated copies after portal purchase". `technical_approach` and `cost_volume`
— the two that matter most — were never written, for any solicitation, ever. And nothing
reconciled the discrepancy: `metadata.json` listed **ten** entries in `section_keys` and **five** in
`artifact_keys`, side by side in the same object.
**Fix** Widened to `[a-z0-9_-]` in BOTH mirrors (the test file declares them mirrors; the frontend
READS what the pipeline writes, so a one-sided fix leaves the frontend unable to address an artifact
the pipeline just stored). Failed writes now collect into `metadata.json` as
`section_artifacts_failed` — the same rule `section_extraction_skipped` already followed ten lines
below. Underscores are safe object-key characters; the widening is purely permissive.
**Proven fixed** 10/10 canonical keys now write and read back a real artifact through the local
storage driver, up from 5/10. The emulator's prose placeholder, `Cover` and `../escape` are all
still refused, so the guard did not loosen into anything-goes.
**Class → sweep for** *a validator that disagrees with the vocabulary it validates*. Wherever a
controlled list is declared in one file (a prompt, a CHECK constraint, an enum, a docs table) and
enforced by a pattern in another, the two drift and the drift is silent. The regression test now
PARSES the canonical list out of the prompt itself, so adding an unwritable key fails loudly in CI
instead of in a warning line during a live shred.

## B43 — A page count guessed from byte size, wearing the name of a measurement · FIXED
**Where** `pipeline/src/shredder/runner.py`, the `solicitation_documents` update
**Proven** The column was written as `len(pdf_bytes) // 40000 + 1  # rough page estimate`, and read
by `packaging_specialist.get_compliance` which hands it to the agent inside the document manifest,
beside values genuinely extracted from the source. Measured against the real solicitations in
`docs/`:
```
DoD 25.2 SBIR BAA      real 254pp   guessed  60    76% low
AF_X24.5_CSO           real  88pp   guessed  17    81% low
Air Force X25.6 v3     real  79pp   guessed  22    72% low
```
**Why it matters** This is the exact failure `docs/INGEST_PROVENANCE.md` exists to prevent: *a value
the product did not read from the solicitation must never look like one it did.* A page-limit
reviewer reading "60 pages" for a 254-page BAA is worse off than one reading nothing, because
nothing invites a check and a number does not.
**Fix** `extractor.pdf_page_count()` reads `doc.page_count` — pymupdf is already opened one function
above to extract the text, so the true count was free the whole time. Returns `None`, never a
fallback number, when the bytes are unopenable or the library is absent; the column is nullable and
the caller stores NULL. Unknown stays unknown, which is the other half of the same rule. Unlike
extraction itself this returns rather than raises: an absent page count must not fail a shred.
**Proven fixed** Real count off a real BAA (254); `None` — not `1` — for empty and non-PDF input,
where the old expression returned `1`, a document claiming to have a page.
**Class → sweep for** *an estimate stored in a field named for a measurement*. Grep for `# rough`,
`# approx`, `estimate`, `// 1000`, and any arithmetic on a byte length that lands in a column a
human or an agent will read as fact. If it cannot be measured, the column must be nullable and the
value must be NULL.

## B44 — Every topic upload failed on an ON CONFLICT that matched no index · FIXED
**Where** `frontend/lib/ingest/ingest-topic-files.ts`
**Proven** `there is no unique or exclusion constraint matching the ON CONFLICT specification` — the
clause named `ON CONFLICT (content_hash)`; the index it arbitrates is two columns:
```
CREATE UNIQUE INDEX idx_sol_docs_hash_per_solicitation
  ON solicitation_documents (solicitation_id, content_hash)
  WHERE content_hash IS NOT NULL
```
so Postgres matched nothing and threw on every call.
**Why it matters** The route still returned **201**, with the error tucked into a per-file `failed`
entry and an empty `created` list. An admin uploading topic files saw "no topics created" and would
reasonably conclude the PDF had not parsed — a data-layer bug wearing the costume of a bad document.
**Fix** Restate the index's own column list AND its WHERE predicate, exactly as the CLAUDE.md data
rule says. Per-solicitation is also the semantics we want: the same PDF under two solicitations is
two legitimate documents; only a re-upload to the SAME solicitation is a duplicate.
**Class → sweep for** *a 2xx that carries a failure in its body*. A route that cannot fail cannot be
monitored. Every per-item `failed[]` array needs either a non-2xx when the list is non-empty, or a
surfaced count the caller must read.

## B45 — The emulator filled a structural key with a prose sentence · FIXED (harness)
**Where** `frontend/scripts/test-harness/emulated-claude.mjs` `emulatedJsonFor`
**Proven** Every non-numeric schema field got
`EMULATED <field> — sandbox harness, not a real extraction`, so the shredder's section `key` arrived
as that sentence — which is not a slug, so B42's validator refused it and the write was skipped.
Net effect: **the sandbox exercised none of the per-section artifact path while appearing to.**
**Why it matters** A harness that silently skips the path it claims to cover is the same defect
class as the product bugs above, one level up. It is also why B42 survived: the only environment
that could have caught it was quietly not running it.
**Fix** The emulator now HARVESTS the controlled vocabulary from the prompt that declares it

Self-maintaining: change the canonical list and the harness follows with nothing here to edit.
**Honesty preserved** Every prose field still reads `EMULATED`. A key is structure, not content, so
emitting a real one does not risk a fixture being mistaken for a real extraction
(docs/INGEST_PROVENANCE.md).
**Class → sweep for** *a fixture generator that fills a typed field with untyped filler*. Any
placeholder that lands somewhere shaped — a slug, a path segment, an enum, an id, a date — is not a
placeholder, it is a wrong value, and the code that rejects it will do so quietly.

## Two bugs found in the fixes themselves, before they landed
Recorded because the point of this log is the class, and "the fix had a bug" is a class.

- **A string-prefix containment check is not containment.** `_local_path` guarded traversal with
  `str(target).startswith(str(root))`. With bucket `testbucket`, the key `../testbucket-evil/x`
  resolves OUTSIDE the root yet still starts with it — precisely the traversal the guard exists to
  stop. Now `Path.is_relative_to`. **Sweep for** any path/prefix/namespace check written with
  `startswith` where the thing being compared is hierarchical.
- **`importlib.reload` leaks module state that `monkeypatch` cannot undo.** A test fixture set env
  vars and reloaded the module to pick them up; monkeypatch reverted the env but not the rebound
  globals, and the leaked `BUCKET` broke an assertion in a LATER file. Now `monkeypatch.setattr` on
  the module attributes directly. **Sweep for** `importlib.reload` in any test that does not restore
  the module afterwards under the original environment.

## B46 — FIXED. `opportunities.solicitation_id` is inconsistently populated
**Found by** the end-to-end arc, on its third run — the first thing it found that a per-stage test
could not.

**Proven.** `solicitation.push` returned 200 with an `opportunityId`, and the bridge fanned out
correctly (bridge=1, **17 tenant cards**). But the opportunity it created has
`solicitation_id = NULL`. Only the FORWARD link is written:
```
curated_solicitations.opportunity_id → opportunities.id     set
opportunities.solicitation_id        → curated_solicitations.id   NULL
```
Across the whole table the back-link is set on 47 of 65 rows, and it does not split cleanly by kind
— 33/47 umbrellas and 14/18 topics have it. So this is not "umbrellas use one link, topics the
other"; it is genuinely inconsistent within both.

**Proven consequence (verification, not product).** `drive-baa-forward.mjs` resolved opportunities
solely through the back-link, so it printed
```
after {"opps":0,"bridge":0,"cards":0,"scores":0}
✗ nothing reached a tenant card
```
against a push that had just created seventeen. It has been reporting failure on success for as long
as pushes have left the back-link NULL — the sixth instance today of *a check that does not touch
what it claims to cover*. Fixed: it now resolves an opportunity through EITHER link.

**NOT proven — the reason this stays open.** The product reads the back-link in 15 places. The two
that matter most defend themselves:
```
opportunity-bridge.ts:88   ON cs.id = o.solicitation_id OR cs.opportunity_id = o.id
republish.ts:160           (same OR)
```
and the bridge's own comment says the two arms exist for umbrella vs topic. But two readers use the
back-link ALONE, with no fallback:
```
compliance-resolver.ts:74  SELECT solicitation_id FROM opportunities WHERE id = $topicId
opportunity-pin.ts:27      JOIN opportunities o ON o.solicitation_id = sd.solicitation_id
```
An inner join on a NULL never matches. Whether that produces a user-visible failure depends on
whether those paths are ever reached with a NULL-back-link opportunity, and **I have not established
that**. It is entirely possible both are only reached for topic opportunities that do carry it.

**What would settle it** — cheap, and worth doing before touching any product code: reach
`compliance-resolver` and `opportunity-pin` with an opportunity created by the push path, and see
whether the result is empty. If it is, the fix is either to write the back-link on push or to give
those two the same `OR` the bridge already has. If it is not, the column is vestigial for umbrellas
and should be documented as such rather than "fixed".

**Second site, found the next run.** `drive-buy-and-build.mjs:69` resolved the opportunity the same
way — `JOIN opportunities o ON o.solicitation_id = cs.id` — and failed with *"no opportunity for
solicitation …, or no tenant lighthouse"* against a solicitation that had just fanned 17 cards. Two
independent scripts written at different times both reached for the back-link, which says the
back-link is the INTUITIVE direction and the forward one is the surprise. That raises the odds that
a product reader has done the same thing somewhere not yet exercised, and it is why this stays OPEN
rather than being written off as a tooling quirk.

Both call sites now resolve through either link, the way `lib/opportunity-bridge.ts:88` already did.

**Class → sweep for** *a bidirectional link where only one direction is written*. Grep for pairs of
tables that reference each other and check which side the writer actually sets. The danger is not
the NULL; it is that half the readers compensate and half do not, so the defect is invisible until a
reader without the fallback is hit.

## B47 — the sandbox self-heal silently invalidated every admin drive · FIXED

## B48 — NOT-A-BUG. `scout_findings.tenant_id`, and a claim I got wrong twice in one hour
**Reported by** schema-check `--unqualified`; **claimed by me** in commit as a real defect;
**retracted** on reading the code.

`drive-scout.mjs` §7 queries `count(*) FILTER (WHERE tenant_id IS NULL) FROM scout_findings`.
The column does not exist — confirmed against the live schema — and the query is wrapped in
`.catch(() => null)`. I wrote it up as textbook Mistake 0: a verification step that silently does
nothing.

**It is the opposite.** The handler I did not read:

```js
if (scoped) {
  check(scoped[0].tenanted === 0, 'findings are platform-scoped, filed under no tenant', …);
} else {
  note('scout_findings has no tenant_id column — platform scope is structural');
}
```

The probe deliberately tolerates BOTH schema shapes and reports the stronger one. If the column
exists, it asserts every finding is filed under no tenant. If it does not, platform scope is not a
property of the data that could drift — it is structural, guaranteed by the absence of the column.
That is a better guarantee than the check it replaces, and the code says so.

**What I actually got wrong, twice, inside an hour:**

1. The checker flagged a column that genuinely does not exist — technically true, materially
   irrelevant, because the query is *expected* to fail. A "column does not exist" finding cannot
   distinguish a mistake from a deliberate schema probe.
2. I then asserted in a commit message that the check "has never actually run", having read the
   `.catch` and stopped there. The failing branch WAS the point.

**Class → sweep for** *a finding that is true about the code and false about the system*. Before
calling a swallowed error a defect, read what the handler does with it. `.catch(() => null)`
followed by a real else-branch is a schema-shape probe, not a silent failure — the same three
characters mean opposite things depending on the ten lines after them.

The genuine lesson is narrower than the one I claimed: my checker needs to stay a LEAD GENERATOR.
Every one of its findings requires a human read before it becomes a bug, which is exactly why the

## B57 — CORRECTED. my own verification command lied, in the exact way this log is about
While checking the B56 fix I ran:

```sh

```


parses as JavaScript. Vitest still passed 1608/1608, because the tests never typecheck that file.

Two rules out of it:
1. **Never put a backtick in a comment inside a tagged template.** Same for `${`.
2. **Capture the exit status of the command you are testing, not the pipeline.**
   `OUT=$(npx tsc --noEmit 2>&1); echo "exit=$?"` — and print the error count, so silence is
   distinguishable from success.

This is Mistake 0 (*a handler that catches its own failure and carries on*) in the verification
harness rather than the product. A green tick I did not earn is worse than a red one I did.

## B61 — FIXED. A solicitation that prints its own page numbers loses every page citation
**Found by** the MT-1 live ingest: all four solicitations reported *"No page markers in the
extracted text — evidence cites excerpts, not page numbers"*, while a direct probe of the same
PDFs had resolved page 2 correctly.

There are **two PDF readers**, and that is the root of it:

| path | reader | output |
|---|---|---|
| `app/api/admin/rfp-upload/route.ts` (synchronous, on upload) | `pdf-parse` | plain text, **injects `-- N of M --` at every page break** |
| `pipeline/src/shredder/extractor.py` | `pymupdf4llm.to_markdown` | markdown, no separators |

The upload route is what fills `solicitation_documents.extracted_text`, deliberately — *"extracting
now beats hoping a worker can fetch them back out of storage."* So the stored text carries
pdf-parse's separator. And a real government solicitation ALSO prints a page footer. Both match
`PAGE_MARKER_RES`, so the marker stream arrives doubled:

```
@  603 '-- Page 1 of 3 --'      ← the document's own footer
@  622 '-- 1 of 3 --'           ← pdf-parse's injected separator
@ 1310 '-- Page 2 of 3 --'
@ 1329 '-- 2 of 3 --'
```

`buildPageIndex` reads 1,1,2,2,3,3, hits `page <= prev.page` with `page !== 1`, concludes "not a
paging scheme at all", and throws away **every** page number. Proven both directions on the live
stored text:

```
stored text (both marker sets)        → pageResolved: false, page 1
same text, document's footer removed  → pageResolved: true,  page 2
```

The value is still read correctly; what degrades is the CITATION — and citability is the entire
reason `pattern_match` outranks `ai` in the trust order. The documents this hits hardest are the
realistic ones, because government solicitations number their pages.

**Fix**: a mark repeating the previous page AND total is the same boundary seen twice — keep the
first, skip the echo. Four tests added, including two that hold the line the fix must not cross:
an erratic 7,3,9 sequence still refuses to resolve, and a genuine document boundary (numbering
restarting at 1) still segments. Mutation-checked: removing the dedupe fails both new assertions.

Two of those tests failed on first run because my fixtures were under `MIN_USABLE_TEXT_CHARS` —
the extractor declining a 110-character "document" is the guard working, not a bug. Padded.

**Class → sweep for** *two producers of the same artifact*. Neither reader is wrong; the defect
lives in the assumption that only one of them exists.

## B62 — FIXED (mig 203). a new tenant is born at 100% of the bucket cap, so it can never author its own scoring lens

**Found**: driving the midterm arc as a real customer. The tenant `northwind-additive` was
onboarded through the public application form, its library was built from its own uploads, and
then the very next thing a customer does — author the lens they want opportunities ranked by —
answered:

```
POST /api/portal/northwind-additive/buckets  →  409
{"error":"You've reached the limit of 6 spotlight buckets. Delete one to add another.",
 "code":"BUCKET_LIMIT"}
```

on a tenant that had authored **zero** buckets.

**Cause**: two correct features whose numbers were set independently and happen to be equal.

- `lib/spotlight/default-buckets.ts` (#104) seeds a starter set on every tenant-creation path
  (`applications/[id]/accept`, `create-tenant`, `create-partner-org`, `partner/own-org`) so fanned
  cards rank on arrival instead of ranking null. That set is **6**.
- Mig 181 moved `automation_framework.max_buckets_per_tenant` **12 → 6**.

Before 181 there were 6 free slots; after, zero. Proven on the live sandbox:

```
 slug               | active_buckets
 northwind-additive |              6      ← all 6 seeded, none authored
```

The design doc states both halves in one sentence, which is where the collision hid in plain
sight — RANKING_SPINE.md §15: *"Cap — global default raised **12 → 6**; keep all 6 seeded
defaults; enforce the cap"*. (It also calls a lowering a raise, which is the tell that the
direction was not being tracked.) The cap is enforced exactly as designed; the seeded set is
exactly as designed; the pair closes the door on the spine's own headline capability, which the
same document opens with: *"bucket authoring → cap → OPP-push rescore"*.

**Why the tests did not catch it**: the cap has a unit test, and it passes — it asserts that
create returns 409 `BUCKET_LIMIT` **at the ceiling**. It builds its own fixture to get there. No
test asked what a tenant's bucket count is the moment it is created, so nothing connected the
seeder's 6 to the cap's 6. This is only reachable by walking in as a new customer.

**Fix** (mig 203 + `lib/automation/policy.ts`): put the two numbers in a relationship instead of
leaving them as independent constants.

- `DEFAULT_MAX_BUCKETS = DEFAULT_BUCKETS.length + BUCKET_AUTHORING_HEADROOM` (6 + 4 = 10)
- `MIN_MAX_BUCKETS = DEFAULT_BUCKETS.length + 1`, and `getMaxBucketsPerTenant` floors any
  configured value at it — so no admin tuning at `/admin/automation-framework` can silently
  re-close authoring either.
- Mig 203 raises the stored cap 6 → 10 **only where it still sits at the mig-181 value**, leaving
  a deliberately-tuned cap alone.

Verified after the fix: cap reads 10, and a freshly-onboarded tenant authors its own bucket.

**Class → sweep for** *a limit and a default that were sized by different authors*. The bug is
not in either number; it is that nothing in the code made them aware of each other. Same shape as
B61 (two producers of one artifact) — a defect that lives in the gap between two correct pieces.

## B63 — FIXED (harness). the drive harness had no action timeout, so one missing selector ate a whole run

**Not a product defect — a test-harness one**, but it is the reason several midterm runs produced
nothing, so it belongs here with the rest.

`playwright.config.ts` set `timeout: 60_000` (per test) and `expect.timeout`, but never
`actionTimeout` or `navigationTimeout`. Both default to **0 in Playwright, which means wait
forever**. The long drives raise the per-test timeout to 30 minutes so the arc can finish, and the
combination is the trap: any `page.fill` / `page.click` / `page.goto` whose target never appears
blocks for the full 30 minutes and the run ends having reached ACT 4 of 8.

Observed exactly that on the arc: the last screenshot written was `06-opportunity-cards.png` at
16:49:32 and nothing moved for the rest of the run — a `signIn()` sitting on
`page.fill('input[name="password"]')`. There was no error to read, because nothing had failed
yet; it was still politely waiting.

**Fix**: bound both in the shared `use` block — `actionTimeout: 20_000`,
`navigationTimeout: 45_000` — so a missing element fails in seconds. On the drives that failure
is caught by the ledger's `step()` wrapper, recorded as `blocked` with its message, and the arc
carries on to the acts after it. `signIn` additionally reports the URL it landed on and the first
200 characters the page rendered, because "sign-in failed" is not a diagnosis and "landed on
/portal/x with no password field" is.

**Class → sweep for** *defaults that mean "infinite"*. A zero in a timeout field reads like
"unset, so something sensible applies" and means the opposite. The tell is a run that produces no
error at all — a hang is not a failure, and only a bound turns it into one.

## B64 — FIXED. The page ruler and the printed page disagreed, in the direction that loses bids
**Found by** building the instrument that was missing: `scripts/calibrate-page-ruler.mts` renders
synthetic documents through the real Chromium exporter and compares the printed page count to
`paginate()`.

`estimatePageCount` decides two things a customer's bid depends on — the gauge they watch while
writing, and the export gate that refuses to advance a volume over its page limit. Both call the
same engine, so they can never disagree *with each other*; that invariant was built deliberately and
it holds. **Nothing ever checked whether either agrees with the page.** The estimator's own comments
record three prior corrections of exactly this class ("a flat height for every image; a footer token
nothing substituted; captions borrowed from alt text"), each found by accident.

Three defects, all under-counting — the direction where the product clears a volume the printer does
not, and the customer is told they are fine:

| case | ruler said | Chromium printed |
|---|---|---|
| 40-row table, single-line cells | 2 | 3 |
| 40-row table, **wrapping** cells | 2 | **4** |
| one sentence of prose above that table | 2 | 3 |

1. **A table row was modelled as 1.35 lines of BODY text.** Measured by binary-searching the
   largest table that still fits one 648pt page, at three cell lengths:
   `1-line 19.64 < row ≤ 20.25pt · 2-line 30.86 < row ≤ 32.40 · 3-line 43.20 < row ≤ 46.29`.
   Solved together those admit `ROW_LINE ∈ (10.8, 12.76)`; 12.0 with a base of 8.0 satisfies all
   three. Reading the stylesheet instead gives `10 × 1.28 = 12.8` from the body's unitless
   line-height — **outside the measured bracket**, because table text resolves at `normal` leading.
   That is precisely why these constants are measured and not derived.
2. **Nothing modelled a cell that wraps.** The old code counted ROWS, so a milestone table whose
   Deliverable column holds a real sentence — the most common table in a proposal — printed a page
   longer and estimated exactly the same. This is the one that mattered.
3. **Columns were assumed equal width.** The table renders `width:100%` with auto layout, so a
   "Month" column holding `1`..`40` takes a sliver and the wide column takes most of the table.
   Splitting evenly made wide columns look narrow, so their text appeared to wrap twice as often as
   it does. Now weighted by each column's longest cell, which is the rule auto-layout uses.

A fourth, in `paginate()` itself rather than the height model: **`fitKeep` refused to relocate an
oversized block.** `table`/`figure` carry `break-inside: avoid` (canvas-html), and Chromium pushes
such an element to a fresh page *even when it cannot fit there*, then overflows. The guard
`h <= usableH` meant the ruler kept flowing it from wherever it landed. Proven directly:

```
table(40 rows) alone                   → 2 pages
ONE sentence of prose + the same table  → 3 pages     (the ruler said 2 for both)
```

**Real-world impact, measured on the four hand-authored proposals in the sandbox** — not synthetic
shapes. Old ruler vs. printed PDF:

```
TVSF-R45  Ohio TVSF Round 45      88 nodes · 6 tables   ruler  9   printed 10   ← a page short
N26D-CAM07 DoW STTR D2P2          45 nodes · 6 tables   ruler  3   printed  4   ← a page short
N261-EXP01 Navy SBIR Phase I      34 nodes · 0 tables   ruler  2   printed  2
TVSF Round 45 (earlier build)     46 nodes · 6 tables   ruler  4   printed  4
```

Two of four were being measured a page short, and both of those carry tables. After the fix all four
agree exactly, and all 15 synthetic cases agree.

**Class → sweep for** *a model of an artifact that nothing ever compares to the artifact*. Two
consumers reading one function agree with each other by construction; that is not evidence either is
right. The check that matters renders the thing and counts.

**Guarding it:** `__tests__/page-ruler-calibration.test.ts` locks the arithmetic (6 cases, no
Chromium needed) and `scripts/calibrate-page-ruler.mts` is the authority, exiting non-zero on any
drift. Re-measure with `scripts/measure-table-row-height.mts` rather than re-guessing the constants.

## B65 — FIXED. A list was measured as a paragraph, so the deck overflow check never fired
**Found by** extending B64's method to decks: `scripts/calibrate-slide-ruler.mts` exports real
`.pptx` files and compares them to `estimateSlideCount` / `overflowingSlides`. No `.pptx` had ever
been produced end to end, so these two had never been compared to a rendered artifact either.

Slide COUNTS were correct on all seven cases — v1 `page_break` splitting, v2 one-section-per-slide,
and the trailing-break edge case. The defect was in HEIGHT, and it turned out to be shared with the
page ruler.

`nodeStackHeightPt` had no case for `bulleted_list` / `numbered_list`, so both fell through to the
flow-text default: **every bullet concatenated into one string and reflowed at full column width**.
Twenty short bullets measured as three lines instead of twenty. Two consequences:

- **Documents**: 120 bullets read 3 pages and printed 4.
- **Decks**: a slide holding 30 bullets — needing ~648pt of a 452pt frame — reported **no
  overflow**. `overflowingSlides` is the only thing standing between a customer and a deck whose
  content is cut off the bottom, and it stayed silent until 60 bullets.

Same shape as B64's table-wrap defect: *the model flattened structure the renderer preserves.*
Fixed by measuring what the stylesheet actually lays out (`ul, ol { margin: 0 0 8pt 20pt }`,
`li { margin: 0 0 3pt }`): one wrapped line-box per item, `+3pt` between items, `+8pt` after the
list, and nested children indented another 20pt per level. The line height uses the stylesheet's
`max(lineSpacing, 1.28)` floor rather than `bodyLineH`, because for a list a fractional error
repeats **per item** instead of averaging out across a reflowed paragraph.

**Two harness mistakes worth recording, because both produced convincing false results:**

1. **`list` is not a NodeType.** The real ones are `bulleted_list` and `numbered_list`. A fixture
   built with `'list'` rendered as nothing and measured as nothing, so the first run showed
   "120 bullets → ruler 1, printed 1 ✓" — a perfect agreement about an empty document. It briefly
   looked like evidence that list content vanishes from exports entirely.
2. **A `.pptx` is a ZIP.** Regexing the raw buffer finds *filenames* (stored uncompressed in the
   local headers) but never the markup, so the first overflow probe reported "no shapes past the
   frame" for every slide, including ones that plainly overflow. Fixed by unzipping properly.

And one honest limit, now written into the script: the pptx exporter **clamps** each box to the
frame (`placeBox`: `Math.min(p?.h ?? defaultH, maxH)`), so overflowing content never appears as a
shape positioned past the slide edge — it is text spilling *inside* a box that fits, which the XML
geometry cannot see. Shape bottoms are still checked (one past the frame would be a worse bug), but
the case is decided on the arithmetic, which is what the script is auditing.

**Class → sweep for** *a model that flattens structure the renderer preserves*. B64 found it in
table cells, B65 in list items. Any node whose content is a LIST of things — rows, items, series,
steps — is a candidate; measuring its text length is not measuring its height.

**Guarding it:** five list cases in `scripts/calibrate-page-ruler.mts` (20/20 agree) plus the deck
harness (7/7), and six unit cases in `__tests__/page-ruler-calibration.test.ts` — including the sharp
one, that the same characters as a list must measure taller than as a paragraph.

## B66 — FIXED (two of three). Sweeping the rest of the node vocabulary for the B64/B65 class
Having named the class in B65 — *a model that flattens structure the renderer preserves* — the
cheap move was to sweep the remaining node types through the same harness rather than wait for the
next one to surface. Twelve node types added to `scripts/calibrate-page-ruler.mts` in one pass.
Two more found, one of them predicted from reading the stylesheet alone:

### `code_block` — FIXED. Newlines were reflowed away
Renders inside `<pre style="white-space:pre-wrap; padding:12pt; font-size:9pt">`, so every `\n` is
a hard line. Measured as flow text it became one reflowed paragraph: **60 lines of code read 1 page
and printed 2.** Now modelled on the `<pre>`'s own geometry, with a monospace advance of 0.6em
(Courier New) rather than the body's proportional 0.45 — using 0.45 would have over-estimated how
much code fits on a line. Exact on both cases (preserved newlines, and one very long wrapping line).

### `toc` — FIXED in isolation, with a NAMED residual. It was modelled as zero height
`nodeStackHeightPt` returned `0` for a contents list, while `buildTocHtml` emits one indented block
per heading in the document. A 40-entry contents list therefore cost **nothing** in the estimate and
two pages in the print.

The height depends on the whole document, which a per-node ruler cannot see, so `paginate()` now
collects the headings once and threads them in (only when the document actually contains a `toc`,
so the common path is untouched). The per-entry height is **measured, not read off the stylesheet**:
binary-searching the largest contents list that still fits one 648pt page gives **31 entries**,
bracketing the entry at `(19.14, 19.76]pt`; the model's 19.36 sits inside it.

**Residual, stated rather than tuned away.** On a document that is a contents list followed by
nothing but headings, the total can still be ±1 page. Isolated component-wise:

```
30×(h2 + prose)  — NO toc     ruler 4  printed 4  ✓
30×(h2 + prose)  — WITH toc   ruler 5  printed 4  Δ-1
40× h3           — NO toc     ruler 2  printed 2  ✓
40× h3           — WITH toc   ruler 3  printed 4  Δ+1
```

Both documents are exact without the toc, and the errors run in *opposite* directions — so this is
not the toc's height. It is `h1,h2,h3 { page-break-after: avoid }` in canvas-html: a heading at the
foot of a page moves to the next page **with its first paragraph**, leaving whitespace the ruler
spends. The ruler does not model that rule. It only bites when something pushes headings onto a page
boundary, which is what a contents list does. Left un-modelled deliberately: it needs the same
measure-then-fit treatment as the table row, and inventing a constant to make two synthetic
documents agree would be fitting noise. Both cases carry an explicit `tolerance: 1` in the harness
with this reason attached.

**Two hypotheses falsified along the way, worth recording because both were plausible:**
- *"The residual is the prose estimator rounding up once per paragraph."* Tested directly — 20/40/60
  short paragraphs versus the same characters as one paragraph — and prose is **exact in both
  forms**. Wrong.
- *"The pptx exporter positions overflowing shapes past the slide frame."* It clamps them
  (`placeBox`), so overflow is text spilling inside a box that fits and the XML geometry cannot see
  it. The deck harness now says so instead of implying a check it does not perform.

### The harness defeated itself, which is the same bug it exists to catch
Adding the `tolerance` field, the default landed at the comparison rather than at the push, so
`r.tolerance` was `undefined` — and **every comparison against `undefined` is false**. The script
printed "← off by −1" beside two rows and then declared "✓ agrees on all 28 cases", and would have
reported success for *any* delta from then on. Caught by noticing the output contradicted itself.

A calibration harness that cannot fail is worth less than no harness, because it is *believed*. The
default now lives at construction, and the run log in this session is the evidence it still fails
when it should: it exited non-zero four times on the defects fixed in B64/B65/B66 before going green.

**Class → sweep for** *a check whose failure path is never exercised*. The instrument deserves the
same suspicion as the thing it measures.

### B40 — the fix (2026-08-22), and what was already done

**Half of this was already built, and the log was stale.** `lib/ingest/source-text-cap.ts` exists:
`capSourceText` caps and reports, `truncationNotice` writes the sentence an admin can act on, and
`extractionOf` reads the stamp back off a document's metadata. The upload route already persists
`metadata.extraction { chars, truncated, originalChars, capChars }`. Checking before rewriting saved
building it twice — the log said "not fixed here" and the code had moved on.

**What was actually missing was the reading end.** `extractionOf` and `truncationNotice` had **zero
callers**. The truncation was recorded faithfully and consulted by nothing — a fact filed where
nobody looks, which is B53's defect (*a metric with no reader*) rather than B40's original one.
And `lib/ingest/ingest-topic-files.ts` still called `capSourceText(...).text` at both sites,
discarding the stamp entirely, so topic files truncated with no record at all.

**Where it surfaces now: the provenance audit.** That is the one place a curator looks before
landing a matrix, and it already carries the vocabulary — `blocker` for provably unfounded,
`warning` for "a person must look". A partly-read document is a **warning**, deliberately:

```
N source document(s) were only partly read — worst: DoW-2026-SBIR-BAA.pdf at 500,000 of
1,013,000 characters (51% not examined). Any field showing a system default may be stated on a
page that was never read, so "not stated in this solicitation" is unverified for this matrix.
```

Not a blocker, because the values that WERE read still stand and the model already lands defaults
wearing a red "unverified" badge; what was missing is the reason they are more than usually suspect.
The blocker case is already covered — if nothing at all was read, `nothingRead` fires regardless of
why. The finding names the **worst** document and states the **share** lost, not just the count:
"we read 500,000 characters" sounds thorough, "51% was not examined" does not.

**Wired at both audit callers** — `stage-skeleton` (every Ingest Assist run) and `assess-ingest` (the
admin's readiness probe) — by selecting `metadata` alongside the document row and mapping it through
`extractionOf`. An absent stamp reads as **unknown**, never as "complete": inventing completeness for
rows ingested before the stamp existed would be the same defect pointing the other way.

**Guarded** by `__tests__/provenance-truncation.test.ts` (10 cases): it fires on a cut document,
names the document and the share, reports the worst of several, stays silent on a whole document,
stays silent on an absent stamp, and does not disturb the findings that were already there.

**Still a product decision, deliberately left to the owner:** whether to raise the 500,000-character
cap, chunk the extraction, or leave it. This change does not touch the number. It makes the
consequence of hitting it visible, which is the part that is required in every one of those worlds —
if the cap is raised, a longer document can still hit it, and the audit will still say so.

**One test-writing note worth keeping.** The first version of the regression matched findings on the
prose `/system default/i`, and the new truncation message legitimately contains that phrase, so it
counted as a second per-field finding and the test failed. Matching on the finding's SHAPE — a
per-field finding carries `field`, a whole-matrix one does not — is the stable predicate.

```
master_templates=0   template_bridge=0   tenant_template_cards=0
```

`TEMPLATE_CATALOG` (39 entries) lives in TypeScript → `syncTemplateStableFromCatalog` →
`master_templates` → `template_bridge` → `backfillTenantTemplates` → `tenant_template_cards`. The
sync was reachable **only** from an admin clicking `/admin/template-stable/sync`, so on a database
nobody had clicked it on the first link never filled — and `backfillTenantTemplates` read zero bridge
heads, applied zero, returned `0`, and all four callers' best-effort `try/catch` treated that as
success.

**Not fixed by seeding the catalog in SQL.** That would copy 39 canvas bodies out of TypeScript into
a migration and let the two drift — the same duplicated-truth problem, one layer down.

**Fixed by treating an empty stable as an anomaly rather than an answer.** When
`backfillTenantTemplates` finds no bridge heads it checks whether `master_templates` is empty, and if
so seeds from the catalog before backfilling. The catalog stays the single source of truth; the sync
is idempotent (it change-detects against the stored body); `master_templates_template_key_key` makes
a concurrent double-run safe; and the check short-circuits forever once master is populated, so the
cost is one pass on the first provision that needs it.

**It repairs backwards, too.** `publishAndFanOutTemplate` inside the sync fans to tenants that
already exist, so the tenants provisioned while the stable was empty are fixed as well — proven live
on the sandbox:

```
[tpl-bridge] template stable is EMPTY — seeding from TEMPLATE_CATALOG before backfill (B34)
[tpl-bridge] stable seeded: 39/39 templates
backfillTenantTemplates → 39 applied

BEFORE   master=  0  bridge=  0  tenant_cards=0
AFTER    master= 39  bridge= 39  tenant_cards=273     (7 tenants × 39, every one of them)
```

**And the silence is closed.** A backfill that applies zero templates now says so, naming the tenant
and how many heads were available. "Found nothing and succeeded" is the shape this defect hid inside
for its whole life, and it is the shape worth refusing on principle — the same refusal as B53's
always-zero tile and B67's grep that could only ever pass.

Guarded by `__tests__/template-stable-selfheal.test.ts` (5 cases) on the contract the self-heal
seeds: the catalog is non-empty, every entry resolves to a real body (an entry without one seeds as
an `error` and silently shortens the shelf), keys are unique against the DB's unique index, formats
are renderable, and every entry carries the title and category a customer sees.

## B68 — FIXED. An image with nowhere to load from was measured as a full-size figure
**Found by** running the mold sweep (`scripts/sweep-mold-quality.mts`, #152) for the first time since
the ruler was calibrated. B64–B66 calibrated against synthetic documents and four hand-authored
proposals, where the ruler is exact. It had never been pointed at the 39 **templates**, and there it
over-counted on 13 of them — by up to 4 pages.

**Not caused by the calibration work, but made marginally worse by it.** A/B against the pre-B64
file on the worst mold: `doe-sttr-phase1-technical` estimated **10** before and **11** after, against
**7** printed. The first A/B I ran said "identical, not mine" — that test was invalid, because
`canvas-document.ts` was already committed, so `git stash` had nothing to revert and both arms ran
the same code. Checking that the file actually changed is what caught it.

**Cause.** `canvas-html::renderImage` emits an `<img>` only when the key is a `data:` URI (the export
path inlines real storage keys first). With nothing to inline it emits a small dashed
`<div style="border:1px dashed;padding:24px">alt</div>` instead, in which the declared height acts as
a `max-height` **cap** rather than a height. The estimator read `content.width/height` regardless.
The molds carry images with an **empty** `storage_key` declared at up to 900×520:

```
image nodes: 5
  key=""  data:URI=false  declared 936x90
  key=""  data:URI=false  declared 900x520
  key=""  data:URI=false  declared 900x520
  key=""  data:URI=false  declared 900x460
```

Five figures at ~390pt of phantom height ≈ the three pages of pre-existing over-count.

**Fix, scoped to the provably-unresolvable case.** An image whose `storage_key` is empty is measured
as the placeholder box the renderer will actually draw. An image with a REAL key is untouched: it
resolves through `inlineImageDataUris` at export and does take its declared size, which is why real
authored proposals measured exactly right and must keep doing so.

**Result — and it is partial, which is why this entry is not FIXED:**

```
                    before   after
molds clean          38/39   39/39
needing a look           1       0     (the investment-pitch-deck violation cleared too)
estimator disagreed     13       9
```

**The first box was guessed, and came out at roughly double.** The fix above read the padding, the
border and the caption off the stylesheet by hand and modelled ~86pt where Chromium lays out 63.6pt.
Two mistakes, both invisible to a reading: the `<figure>`'s 12px margins were charged twice when they
COLLAPSE against the neighbouring paragraph's, and a caption line was charged to a box with no
caption. `scripts/measure-image-placeholder.mts` asks the renderer instead — lay the figures out,
report where each one starts — and the top-to-top delta IS the height to charge:

```
empty key, no declared size        inner   70.5px   advance  61.85pt   (in a run of figures)
empty key, declared 900x520        inner   70.5px   advance  61.85pt
empty key, declared 320x60         inner   60.0px   advance  54.00pt   (max-height caps it)
empty key + caption                figure  89.8px   advance  76.37pt
empty key, long alt (wraps)        inner  111.4px   advance  92.55pt
marginal cost interleaved with prose                        63.60pt
```

Model now: `36pt padding + 1.5pt border + lines × bodyLineH`, capped by the declared height, plus
14.5pt for a caption and an 11pt collapsed figure gap — 63.86pt against 63.76pt measured on the same
document. Five placeholder cases are now in the calibration harness, which had none.

**The remaining molds were a different bug — see B69 and B70.** Diagnosing them needed a sharper
instrument than "estimates 7, prints 5", so `scripts/diagnose-mold-ruler.mts` and the
`nodeHeightsPt` read-out were built: `--nodes` charges every node against the height Chromium gives
that same node in place, `--segments` does it per page-break segment, `--pages` replays the ruler's
own placement. Amplifying one node type ×240 — the method used before — LIES about anything with a
vertical margin, because a run of forty headings collapses margins a real document does not; it
reported headings +29% and images +84% where both were exact.

**Result after B69 and B70 as well:**

```
                    before   after B68   after B69   after B70
molds clean          38/39        39/39       39/39       39/39
estimator disagreed     13            9           4           4
```

**Class → the calibration set has to include the artifacts the product ships,** not only the ones a
harness invents and the ones a person happened to author. Templates are content the customer sees on
day one and they were the least-measured content in the system.

## B69 — FIXED. A running header was charged twice, taking 11% off every page
**Found by** chasing B68's remaining nine molds with a per-node instrument instead of a page count.
The per-node comparison came back almost perfect — `nsf-sbir-phase1-project-description` modelled its
whole 56-node body to within **2pt** of Chromium — and the ruler still said 8 pages against a printed
6. That rules out the heights and points at the FRAME, which nothing had ever measured.

**Cause.** `flowMetrics` computed the content box as

```ts
usableH = height − margins.top − margins.bottom − (header?.height ?? 0) − (footer?.height ?? 0)
```

but `exportToPdf` passes the canvas margins straight to `page.pdf({ margin })` and sets
`displayHeaderFooter`, and Chromium draws those templates **inside** the margin box. The content box
is `height − top − bottom`, full stop. The editor's page frame agrees — `canvas-renderer` positions
the header and footer absolutely in the margin bands. So a document with both lost 72pt of a 648pt
page, on **every page**: 11%.

Every agency mold the product ships carries a running header and a page-numbered footer.

**Why nothing caught it.** All 28 calibration cases used `CANVAS_PRESETS.letter_standard`, the one
preset that declares `header: null, footer: null`. The furniture path had no measurement at all. Two
more cases in that file were worse than useless: `frame · narrow margins` and `frame · 12pt body`
passed `{ margin_in: 0.5 }` and `{ body_pt: 12 }`, which are not fields of `CanvasRules` (`margins`
and `font_default` are), so the override landed as an ignored property and both cases silently re-ran
the plain two-page prose case. A frame variation that does not vary the frame is this harness's own
defect class, one level up.

**Measured, before the fix:**

```
prose · ~4 pages                                     ruler 3   printed 3
frame · running header + footer, 4 pages of prose    ruler 4   printed 3   ← same prose
```

**Fix.** `usableH = height − margins.top − margins.bottom`. Three furniture cases added to the
calibration harness (header+footer over prose, header+footer over a mixed volume, footer alone), the
two dud frame cases repaired to vary what they claim to vary, and a unit test
(`__tests__/page-ruler-frame.test.ts`) that pins furniture as free and margins as not — the second
half guarding against over-correcting.

**Result:** mold disagreements 9 → 4, every one of them still in the over-counting direction.

**Class → a default that switches off the thing under test.** The preset every case reached for had
the feature nulled out, so the harness grew to 28 cases without once exercising a path the product
uses everywhere. Same shape as B66's tolerance defaulting at the comparison, and as B67's grep.

## B70 — FIXED. A table column was starved below the width of the word inside it
**Found by** `diagnose-mold-ruler.mts --nodes` on the NSF Project Description mold: one table node
modelled at **148pt** against **105.9pt** printed, a 40% over-count on a single node, which was most
of the 78pt that pushed one page-break segment onto a second page.

**Cause.** B64 replaced equal-width columns with a share proportional to each column's longest cell —
right in direction, wrong at the narrow end. The milestone table's first column holds `Task 1`; its
proportional share came to **5.8 characters**, so the model wrapped a six-character cell onto a second
line, on every row.

CSS auto table layout does not work that way (CSS 2.1 §17.5.2): every column first gets its
**min-content** width — the longest unbreakable word — and only what is left over is shared out, in
proportion to how much more each column wants (`max-content − min-content`). When the max-contents
all fit, nothing wraps at all.

**Fix.** That algorithm, plus `Math.round` rather than `Math.floor` on the per-column character
allocation: flooring stacks a second conservatism on top of `CHAR_W`'s (0.45 against a measured ~0.42)
and stacks it once **per column**. The table above: 148pt → 124pt against 105.9pt printed.

**Result:** the milestone table 148pt → 124pt against 105.9pt printed. What was left of the
over-count then turned out to be two more defects — B71 and B72 — which the mold numbers alone
could never have separated.

## B71 — FIXED. Every line of prose was measured 11% short of the leading it renders at
**Found by** doing what should have been done before touching the ruler at all: measuring it
against REAL authored proposals. `scripts/verify-ruler-on-proposals.mts` runs the eight NILOC gold
volumes — full narratives, agency shape, page-numbered footers — through the product's own exporter.
Molds cannot answer this question; their content is brackets.

**The result was alarming and correct to be alarmed by:**

```
                        before this session   after B69   after B71
under-counted                    2 of 8         4 of 8       0 of 8
```

B69 did not create the under-count. It REMOVED THE MASK. Subtracting 72pt of furniture from every
page was hiding a defect that ran the other way, and correcting one exposed the other — which is
exactly why the safety property has to be measured on the artifacts that matter, not inferred from
"the direction of my change was conservative."

**Cause.** `canvas-html::canvasBaseCss` sets `line-height: Math.max(lineSpacing, 1.28)`, with its
own comment explaining why ("a solicitation that mandates single spaced means 1.0 of the LEADING a
typesetter would use"). `flowMetrics` computed `bodyLineH = fs * c.line_spacing` — the raw value.
On `letter_standard` (1.15) every line of prose was modelled at 13.8pt where the page draws 15.36pt.
11% short, on the most common node in a proposal.

Four node cases had already worked around it LOCALLY — lists, code_block, toc and the figure
placeholder each carry `Math.max(m.bodyLineH / fs, 1.28)`. The flow-text default, which is most of a
volume, had not. A local workaround repeated four times is the shape of a fact that belongs one
level up.

**Fix.** The floor moves into `flowMetrics`. The four local copies are now no-ops and stay as
documentation. All eight authored proposals land exact.

**Class → a constant duplicated at the call sites instead of computed once.** Nobody wrote the
model wrong; four people wrote the correction right, in four places, and the fifth caller never got
one.

## B72 — FIXED. The ruler charged margins the page collapses
**Found by** the same measurement: with B71 alone the prose was right and the page counts still
drifted, so the remaining error had to be BETWEEN nodes rather than inside them.

**Cause.** The ruler charged every node its full box plus margins, and did it inconsistently — a
heading carried its 20pt and 5pt, a figure carried both of its own, a paragraph carried nothing at
all (`p { margin: 0 0 7pt }` was simply absent from the model), a table carried neither. CSS
collapses adjacent vertical margins to the LARGER of the two, so:

```
                                real        old model
paragraph, then paragraph        7pt          0pt      (under)
paragraph, then <h2>            14pt         14pt      (right, by accident)
paragraph, then <figure>         9pt         18pt      (over)
```

**Fix.** `nodeMarginsPt(node)` gives every type its real `{top, bottom}` read off canvas-html, the
node heights become BOXES, and both stackers collapse: `max(previous.bottom, current.top)`. Two
rules that paged CSS applies and a first pass will miss — a margin at the TOP of a page is not spent
(charging it put `y` above zero before the first element, so `fitKeep` treated a table at the top of
a page as one to relocate, and a 2-page table landed on pages 2 and 3 of a 3-page document with
nothing on page 1), and a keep-together block's own outer margins collapse through it.

**And one more, found on the way:** a `chart` fell through to a flat `fs * 15.5` guess because chart
nodes carry no width or height — 201pt modelled against 256pt printed, a 21% UNDER-count. But
`renderChartSvg` fixes its own viewBox (480×300 for every plot type; 500 × (12 or 30 + 24/category +
26) for a gantt), so the height is computable. Measured with `scripts/probe-chart.mts` before being
written down.

**Where the ruler stands now**, across every instrument built for it:

```
authored proposals (8, NILOC)      8 exact, 0 under-counted
calibration cases (36)             36 agree, 4 within a stated ±1, 0 under-counted
deck cases (7)                     7 agree
templates (39)                     39 clean, 5 over-count by 1-2 pages, 0 under-counted
```

**The remaining five molds are one known cause, and it is not a constant to nudge.** `CHAR_W` is a
single number standing in for a font whose real average advance depends on the words. Measured on
40-line paragraphs so line quantisation cannot dominate (`scripts/measure-char-width.mts`, and the
first version of that script was wrong for exactly that reason — a 4-line sample reported the same
"4 lines" at 10pt and at 12pt, which cannot both be true):

```
lowercase technical prose   0.41      long compound words   0.44-0.47
numerals and identifiers    0.42      acronym-dense text    0.58
```

0.45 is the average of those, so it runs ~10% conservative on lowercase and ~20% optimistic on
capitals. Molds are bracket-heavy lowercase, which is the register where it is most conservative;
authored proposals mix all four, which is why they land exact. Closing the last five means
estimating the advance PER TEXT from its character mix — a real change with its own risks, done with
the harness watching, not a constant moved late in a session.

**Direction matters and is worth being explicit about:** over-counting cannot clear a bid the gate
should refuse. It is still wrong — it would tell someone their 6-page volume is 8 — but it is wrong
safely, and on molds, which are skeletons a customer fills.

**Class → correcting one error can expose another that was cancelling it.** Two of the three defects
here (B69 over, B71 under) were partly hiding each other, and the mold sweep — over-counts only —
could not see the under-count at all. Only measuring the real artifact could.

## B73 — FIXED. The ruler died on a canvas the exporter draws happily
**Found by** pointing the ruler at the artifacts that are actually IN THE DATABASE. B71's harness
(`verify-ruler-on-proposals.mts`) measures the eight NILOC volumes, which are markdown on disk
converted at run time. `scripts/verify-ruler-on-stored-artifacts.mts` measures the other thing —
real `proposal_artifacts` rows with their real sections, groups, furniture and stored images,
assembled by `assembleArtifactCanvas`, the SAME assembly the layout route and every export path
use. Three of twenty-two threw before they could be measured:

```
TVSF Round 45 · Narrative                 estimatePageCount THREW  ·  exportToPdf → 122,984 bytes
TVSF Round 45 · Willingness-to-License    estimatePageCount THREW  ·  exportToPdf →  11,432 bytes
TVSF Round 45 · ESP Support Letter        estimatePageCount THREW  ·  exportToPdf →  11,432 bytes
```

**Cause.** Those volumes carry a PARTIAL canvas spec — `{width, height, margins}` and no
`font_default`, no `line_spacing`, no `format` — and `flowMetrics` read `c.font_default.size`
directly: `TypeError: Cannot read properties of undefined (reading 'size')`. `paginate` guards a
MISSING canvas (`doc.canvas ?? CANVAS_PRESETS.letter_standard`); nothing guarded a partial one.

**The asymmetry is the defect.** `canvasBaseCss` defaults every field it reads
(`font_default ?? { family: 'Times New Roman', size: 12 }`), so the very same volume downloads as a
correct PDF — 122KB of it — while the page gauge (`canvas-renderer`), the layout route's "8 / 15
pages" panel, `computeSubmissionReadiness`, `document-furniture` and `volume-finish` all throw on
it. One half of the system tolerant of real data, the other half brittle, over the same rows.

**Fix.** `flowMetrics` fills a partial spec from `FRAME_DEFAULTS` — canvas-html's defaults,
deliberately, so the ruler measures the document the exporter will actually draw rather than
refusing to measure at all. Four unit cases in `__tests__/page-ruler-frame.test.ts`, including the
guard against over-correcting: a partial canvas that DOES declare wider margins must still change
the answer.

**Result:** 22 of 22 stored volumes now measure, and all 22 agree with the printed page exactly —
including the 9-page TVSF Narrative, the largest real document in the set.

**Class → the fixture that never fails is the one built from a template.** Every canvas the
calibration harness, the unit tests and the mold sweep had ever seen was constructed by
`CANVAS_PRESETS`, which is complete by construction. Rows a customer's data actually contains are
not, and nothing in the test suite had ever handed the ruler one.
