# Sample Proposal — Aerivio Systems (fictional) → USAF AFWERX SBIR Phase I (CSO)

A **100% complete, fully fictional** proposal built to exercise the RFP Pipeline
proposal engine end-to-end: multiple volumes, multiple artifacts per volume,
multiple canvas types, per-canvas draft→save→lock, the hierarchical lock/push
(section → artifact → volume → proposal), and export to every deliverable format.

**These are our canonical example outputs / templates** — point to them to show
what a finished proposal looks like across formats, and reuse the canvas JSON in
`canvas/` (see below) as starting templates.

- **Company (made up):** Aerivio Systems
- **Technology (made up):** quantized 4-bit edge-AI acoustic threat classification
  on unmanned surface vessels — on-vessel inference under a 2-watt ceiling, <100 ms,
  a dual-use DoD maritime autonomy capability (Air Force & Navy autonomous hulls +
  commercial maritime security)
- **Solicitation (made up):** AFWERX SBIR Phase I (CSO), Topic N251-042
  "Autonomous Acoustic Threat Classification at the Tactical Edge", $150k / 6 months

> Everything here is fabricated for a functionality demonstration. No real
> company, person, agency record, or award is represented. AFWERX is the Air Force
> SBIR vehicle; the maritime technology is framed as a dual-use DoD (Air Force /
> Navy) capability, consistent throughout the volumes.

## The lifecycle these exercise (RFP admin + shadow support)

The deliverables above are the **example outputs**. The **full lifecycle** — the
real ingest → curate → build → lock → library → export loop — is emulated
end-to-end in `frontend/scripts/usaf-cso-e2e.mts` against the live schema:

```
ingest     USAF AFWERX CSO (Topic N251-042) → opportunity
matrix     the 11 AFWERX/DoD Phase I required elements → proposal_compliance_matrix
skeleton   4 volumes · 5 artifacts (canvas documents) · molded sections per CSO spec
draft      each section drafted (canvas JSON) and styled
lock       section-by-section → compliance matrix advances to 5/5 SATISFIED;
           the Supporting Documents volume forces format='pdf'
library    each locked section harvests into library_atoms as a SEMINAL primitive
           atom, bound into the proposal's document cocoon (the foundational doc)
export     docx / pptx / xlsx / pdf assembled FROM the locked sections
```

Every lock — whether a single canvas or a hierarchical push — runs the identical
per-canvas stricture (`lib/proposal/lock-section.ts::lockSectionCore`): CAS lock,
`section.locked` event, compliance-matrix → satisfied, canvas snapshot, **library
harvest**, then the artifact / volume / proposal roll-ups. The hierarchical push
(`.../lock-scope`) simply loops that core, so "close + move" at any level is fully
audited per canvas.

### The atom loop (why every locked doc is a foundational document)

On lock, `lib/proposal-atom-harvest.ts::harvestSectionToAtomLibrary` returns each
section to the unified library as a selectable **primitive** atom, meta-tagged on
**both** Dewey axes so it can be found by content OR context for the next mold:

- **content-class** — `kind` (e.g. `narrative`) + `vol` (from `section_type`)
- **source-context** — the "FROM" pedigree pulled from the proposal's opportunity:
  `agency` · `program` · `phase` · `sol` · `topic`

Those context tags feed the `ctxMatches` ranking in the selection query
(`lib/atoms.ts`, dimensions `agency/program/phase/tech/dept`), so the **next**
AFWERX CSO surfaces these atoms with high context alignment, while a Navy effort
surfaces them for re-context (new agency/sol tag + refactor) with lineage
preserved — the reuse loop the platform is built around.

## Regenerate

```bash
cd frontend
npx tsx scripts/gen-sample-proposal.mts   # writes the 6 files here + canvas/ templates
```

PDF export uses Chromium via Playwright (`PLAYWRIGHT_CHROMIUM_EXECUTABLE` or an
auto-detected `chromium-*` under `PLAYWRIGHT_BROWSERS_PATH`); the docx/pptx/xlsx
exporters are pure Node (no browser).
