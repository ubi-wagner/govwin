## 1. What this session was

The tail of the full-scope run: close the remaining phase items, then report. Both items still open
had been filed as minor — a null column with "no reader", and an emulator string that "wasn't a
valid slug". **Both were wrong.** Reading each one through turned up a product defect, and the
second one turned up a third defect behind it.

That is the honest headline: my own triage was the thing that had kept these hidden, not the
difficulty of finding them.

---

## 2. The four bugs, in one sentence each

| | Bug | Where it hid |
|---|---|---|
| **B42** | The section-slug rule rejected 5 of the shredder's own 10 canonical keys | `log.warning` inside a per-section `try/except` |
| **B43** | `page_count` was `len(pdf_bytes) // 40000 + 1` — a byte guess in a column named for a measurement | Nowhere; nobody had read the line |
| **B44** | Every topic upload failed on an `ON CONFLICT` matching no index | A `201` with the error inside a `failed[]` entry |
| **B45** | The emulator filled the section `key` with a prose sentence, so the sandbox never ran the artifact path | The harness, silently skipping what it claimed to cover |

**The common shape** — and the reason a green suite proved nothing here — is a handler that catches
its own failure and carries on. Each produced a run that reported success having done less than it
claimed. Now recorded as **Mistake 0** in `CLAUDE_CLIFFNOTES.md` §4, at the top of the list, because
it outranks every column-name bug below it.

Two further bugs were found *in the fixes*, before they landed (string-prefix containment;
`importlib.reload` leaking module state). Both are in the log and in the commit messages rather than
quietly squashed.

## 3. What is now proven, that was not before

- **10/10 canonical section keys write and read back a real artifact**, up from 5/10 — driven
  through the pipeline's new local storage driver, not asserted from the regex.
- **The page count is read, or absent.** Real count off a real 254-page BAA; `None` — not `1` — for
  empty and non-PDF input.
- **The pipeline can store at all in this sandbox.** It had no local driver, so every call needed
  boto3 (absent), and the shredder's `except` turned that into "S3 fetch failed … skipping".
- **The regression tests parse the vocabulary from its own source.** Adding an unwritable canonical
  key now fails in CI, not in a warning line during a live shred.

## 4. What is NOT proven — read this before trusting the green

- **The full e2e suite has not completed since the fixes.** Two runs were killed mid-flight by
  container restarts (one ~9 minutes in with zero failures). The last *complete* run was
  **147 passed / 0 failed / 24 skipped**, taken BEFORE the three fix commits. The unit suites did
  complete on the current code: tsc 0 · vitest 1606 · pytest 1292.
- **The screenshots in `docs/manuals/img/` predate the fixes.** They were re-captured at 05:21 from
  the all-green run; `966ee159`, `7a0295c8` and `789041b4` landed after. Three of the four defects
  have no UI surface to photograph (storage layer, a nullable column, a SQL clause) — only B44's
  topic upload does.
- **B42's real-world effect is inferred, not observed.** Every `solicitation_documents` row in this
  sandbox has `page_count IS NULL` and no shredded-section artifacts, because the doc-row update sits
  downstream of the S3 fetch that could not run without boto3. The defect was found by reading, and
  proven by construction (10/10 keys through the driver) — not by watching a real shred recover.
  **A real shred against a real BAA, post-fix, is the outstanding proof.**
- **J10 (tenant-side amendment fan-out)** and **J13 (concurrency + malformed payloads)** remain
  partial, exactly as at the last close-out. Nothing this session touched them.

## 5. Sandbox

Eleven container restarts across this drive, three of them in the final stretch. The self-heal
earned its keep — the last one printed, unprompted:

```
UNHEALTHY (4 service(s)):
  emulator: POST /v1/messages failed
  worker:   not running
  frontend: /login not serving
  fixtures: missing — lighthouse-tenant e2e-logins
  build:    STALE — page.tsx is newer than .next/BUILD_ID
          repaired — stack healthy again
```

37–50 seconds, one command, fixture accounts included. The probe then correctly flagged a stylesheet
400 (the background rebuild had swapped `.next` under the running server) — which is what a health
check is for, and why giving it a CLI dispatch mattered.

**One near-miss worth recording.** I ran a negative control against `probe_frontend` by overriding
`APP_URL`, saw it still exit 0, and began writing it up as broken. It hardcodes `localhost:3000` and
never reads that variable — the control tested nothing. Verified the stack independently instead.
*A negative control that does not touch the code path under test is not evidence.*
