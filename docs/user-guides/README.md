# RFP Pipeline Portal — User Guides & End-to-End Coverage Map

This is the home for **user-facing guides** (how each person uses the product,
with screenshots) **and** the **complete end-to-end task map** — every capability
each role touches, from first login to a submitted proposal, tracked as a
checklist so nothing is left undocumented.

Screenshots are **real captures of the running app** (retina PNGs under
[`./img/`](./img)), regenerated by a Playwright harness — see
[Regenerating screenshots](#regenerating-screenshots).

---

## The five roles

| Role | Who they are | Home surface |
|---|---|---|
| **master_admin** | Full system access — migrations, tenants, every admin tool | `/admin` |
| **rfp_admin** | RFP triage/curation, customer onboarding, release, support | `/admin` (+ tenant shadow) |
| **tenant_admin** | The customer's owner — buys proposals, builds, invites the team | `/portal/[tenant]` |
| **tenant_user** | A customer teammate — access per admin grant | `/portal/[tenant]` |
| **partner_user** | An external collaborator — scoped to specific sections | collaborator landing |

> One canvas, many roles. The document editor is the **same shell** for everyone;
> only the sidebar tools light up differently by role × stage × document type
> (see the [Documents guide](./documents.md) and
> [`docs/CANVAS_GEOMETRY_REDESIGN.md`](../CANVAS_GEOMETRY_REDESIGN.md) §8a).

## How the guides are structured

Each guide follows the same shape so a reader can self-serve:

1. **Who this is for** + what you'll accomplish.
2. **Prerequisites** (role, prior state).
3. **Numbered steps**, each with a real screenshot and the exact button/label to click.
4. **What just happened** (the system-side effect, in plain language).
5. **Troubleshooting / known friction**.

## Regenerating screenshots

Screenshots come from the live app via a Playwright harness
(`frontend/scripts/capture-shots.mts`). To refresh them:

```bash
# 1. Point at a database and start the app
cd frontend
DATABASE_URL=…  AUTH_SECRET=…  node node_modules/next/dist/bin/next start -p 3000 &

# 2. (sandbox only) give the demo users a known password + seed demo templates
#    — see scripts in the session scratchpad; never do this against production.

# 3. Capture a journey (documents | portal-tour | proposal | admin | todos | collab | ingest | audit)
BASE_URL=http://localhost:3000 PLAYWRIGHT_BROWSERS_PATH=/opt/pw-browsers \
  node --import tsx scripts/capture-shots.mts documents
```

The harness logs in through the real login form, walks the journey, and writes
retina PNGs to `docs/user-guides/img/`. It launches the pre-installed Chromium
via `executablePath` (the project pins a newer Playwright than the cached
browser), so no `playwright install` is needed.

> **Demo data.** Guides are shot against a seeded demo tenant (**Acme Navy
> Systems**) so screens are populated. Your real screens show your own data. The
> **opportunities are real current DoD SBIR 2026 (DSIP) topics** — DARPA DSO/BTO
> and NAVWAR FY26 releases (MANTRAS, ExCAIPE, FALCON, …) — seeded via
> `frontend/scripts/seed-dsip-opps.mts`, which drives the product's own
> publish→fan-out so they land on both the admin triage queue and the tenant
> spotlight (auto-scored). Codes/titles/dates verified from public sources
> (dodsbirsttr.mil / darpa.mil).
